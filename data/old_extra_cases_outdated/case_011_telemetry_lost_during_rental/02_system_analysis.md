# UC. Потеря телеметрии во время аренды

## Назначение

Сценарий описывает backend-процесс обработки потери телеметрии автомобиля во время активной аренды.

В документе используются рабочие термины из бизнес-домена каршеринга. Иногда один и тот же объект называется по-разному: “поездка”, “аренда”, `rental session`; “машина”, “автомобиль”, `vehicle`. Для анализа нужно считать эти термины близкими по смыслу.

## Шаг 1. Получение исходного состояния

Backend получает входящий REST-запрос, связанный со сценарием. В зависимости от операции используются запросы к пользователю, автомобилю, бронированию, аренде, платежу или связанным сущностям.

Для первичной проверки выполняется чтение из таблиц:
- `users`;
- `vehicles`;
- `bookings`;
- `rental_sessions`;
- `payments`;
- `outbox_events`.

Если ключевая сущность не найдена, дальнейшее выполнение сценария невозможно.

## Шаг 2. Проверка пользователя

Backend проверяет, что пользователь существует, не заблокирован, имеет статус `VERIFIED`, не имеет критической задолженности и ограничений, которые запрещают выполнение текущей операции.

Для проверки используются:
- `users`;
- `user_status_history`;
- `user_debts`;
- `user_restrictions`.

Часть ограничений может приходить из risk-service. Поведение risk-service еще не полностью унифицировано между окружениями.

## Шаг 3. Проверка водительского удостоверения

Если операция связана с бронированием или стартом аренды, backend проверяет водительское удостоверение.

Проверяется:
- наличие документа;
- статус `VERIFIED`;
- срок действия больше текущей даты;
- отсутствие статуса `REJECTED`.

Используются таблицы:
- `driver_licenses`;
- `driver_license_verification`.

Стаж вождения в текущей версии обычно не используется, хотя ранее обсуждалось ограничение 2 года.

## Шаг 4. Проверка автомобиля

Backend проверяет состояние автомобиля.

Проверяется:
- автомобиль существует;
- статус соответствует ожидаемому состоянию;
- отсутствует техническое обслуживание;
- отсутствует блокировка;
- нет несовместимых активных бронирований или аренды.

Используются:
- `vehicles`;
- `vehicle_status`;
- `vehicle_maintenance`;
- `vehicle_telemetry`;
- `bookings`;
- `rental_sessions`.

Статус в БД считается источником истины. Kafka-события используются для распространения изменений, но не для принятия решения о текущем состоянии.

## Шаг 5. Выполнение основной операции

Backend выполняет основную операцию сценария: создает или изменяет бронирование, аренду, платеж, штраф, damage report, refund или связанную сущность.

Операция выполняется в транзакции. Перед commit повторно проверяются критичные статусы, чтобы избежать гонок.

В зависимости от сценария изменяются:
- `bookings`;
- `vehicles`;
- `rental_sessions`;
- `payments`;
- `refunds`;
- `fines`;
- `damage_reports`;
- `user_debts`;
- `user_restrictions`.

Если проверка не пройдена, бизнес-сущности не должны изменяться.

## Шаг 6. Работа с Kafka и outbox

После успешного изменения данных backend создает записи в `outbox_events`.

Типы событий зависят от сценария:
- `BOOKING_CREATED`;
- `BOOKING_CANCELLED`;
- `BOOKING_EXPIRED`;
- `RENTAL_STARTED`;
- `RENTAL_FINISHED`;
- `VEHICLE_RELEASED`;
- `PAYMENT_CREATED`;
- `PAYMENT_CAPTURED`;
- `PAYMENT_FAILED`;
- `PAYMENT_REFUNDED`;
- `FINE_CREATED`;
- `DAMAGE_REPORT_CREATED`;
- `TELEMETRY_LOST`.

События публикуются в Kafka после commit.

Если операция завершилась ошибкой, бизнес-события успешного сценария не должны создаваться.

## Шаг 7. Проверка альтернативного поведения

Backend должен корректно обрабатывать альтернативные потоки:
- сущность не найдена;
- статус изменился конкурентным процессом;
- истек TTL;
- платежный провайдер вернул ошибку;
- geo-service недоступен;
- телеметрия устарела;
- Kafka временно недоступна;
- Notification Service недоступен.

Часть поведения зависит от конфигурации окружения. В таких местах постановка оставляет небольшую неоднозначность, как это обычно бывает в рабочих документах.

## Шаг 8. Проверка отсутствия лишних изменений

Если операция отклонена, backend не должен:
- создавать лишние записи;
- менять статус автомобиля;
- создавать платеж;
- публиковать события успешного сценария;
- дублировать уже существующие сущности.

Для контроля используются:
- статусные таблицы;
- audit таблицы;
- outbox;
- финансовые таблицы.

## Шаг 9. Аудит

Backend должен сохранять audit information:
- идентификаторы сущностей;
- предыдущие статусы;
- итоговые статусы;
- причину операции;
- источник операции;
- timestamp;
- correlation id.

Для хранения используются:
- `audit_logs`;
- доменные audit-таблицы;
- `request_history`.

## Шаг 10. Итоговое состояние системы

После выполнения сценария данные должны находиться в согласованном состоянии. Все изменения должны соответствовать ФЛК, статусной матрице и допустимым переходам.

ИИ-модель должна извлечь из этого описания цепочки API, предусловия, постусловия, проверки ФЛК, альтернативные потоки, негативные проверки, граничные значения и интеграционные проверки.
