UC-005. Повторная отмена уже отменённого бронирования
Название сценария

Проверка защиты от повторной отмены бронирования, которое уже находится в статусе CANCELLED.

1. Бизнес-контекст

Система каршеринга разрешает отмену бронирования только в том случае, если оно находится в активном состоянии. После того как бронирование однажды отменено и переведено в статус CANCELLED, любая последующая попытка повторной отмены того же бронирования должна быть отклонена.

Данный сценарий проверяет корректность конечного автомата состояний бронирования: система не должна допускать перехода из состояния CANCELLED обратно в CANCELLED через повторный вызов операции отмены.

2. Участники сценария
Участник	Описание
Пользователь	Выполняет первичную отмену, затем повторно инициирует отмену того же бронирования
API Gateway	Принимает REST-запросы клиента и маршрутизирует их
Booking Service	Управляет состояниями бронирования, проверяет допустимость операции отмены
Vehicle Service	Обновляет статус автомобиля при отмене бронирования

3. Предусловия

Сервис доступен по REST API.
В системе существует как минимум один автомобиль со статусом AVAILABLE.
Пользователь с идентификатором {{user_id}} существует в системе и не заблокирован.
Переменная {{startDate}} содержит корректную дату в будущем в формате ISO 8601.
Переменная {{city}} содержит наименование города для поиска доступных автомобилей.

4. Основной поток сценария

Шаг 1. Получение списка доступных автомобилей

Пользователь выполняет запрос на получение доступных автомобилей в указанном городе.

Метод и URL: GET /v1/vehicles/available?city={{city}}

Ожидаемый HTTP-статус ответа: 200 OK.

Система возвращает список автомобилей со статусом AVAILABLE. Из полученного списка извлекается vehicleId первого автомобиля.

Результат шага:

переменная {{vehicleId}} содержит идентификатор доступного автомобиля;
список содержит как минимум один элемент.

Шаг 2. Создание бронирования

Пользователь отправляет запрос на бронирование выбранного автомобиля.

Метод и URL: POST /v1/bookings

Тело запроса:
{
  "userId": "{{user_id}}",
  "vehicleId": "{{vehicleId}}",
  "startDate": "{{startDate}}"
}

Ожидаемый HTTP-статус ответа: 201 Created.

Система создаёт бронирование, устанавливает статус CREATED и переводит автомобиль в статус BOOKED. Из тела ответа извлекается и сохраняется bookingId.

Результат шага:

создано бронирование;
переменная {{bookingId}} содержит идентификатор созданного бронирования;
статус бронирования — CREATED.

Шаг 3. Первичная отмена бронирования

Пользователь отправляет запрос на отмену ранее созданного бронирования.

Метод и URL: POST /v1/bookings/{{bookingId}}/cancel

Тело запроса: отсутствует.

Ожидаемый HTTP-статус ответа: 200 OK.

Система проверяет существование бронирования и допустимость перехода в состояние CANCELLED. Переводит бронирование в статус CANCELLED и возвращает автомобиль в статус AVAILABLE.

Тело ответа должно содержать поле status со значением CANCELLED.

Результат шага:

бронирование успешно отменено;
статус бронирования изменён на CANCELLED;
автомобиль {{vehicleId}} переведён в статус AVAILABLE.

Шаг 4. Повторная попытка отмены уже отменённого бронирования

Пользователь повторно отправляет запрос на отмену того же бронирования, которое уже находится в статусе CANCELLED.

Метод и URL: POST /v1/bookings/{{bookingId}}/cancel

Тело запроса: отсутствует.

Ожидаемый HTTP-статус ответа: 409 Conflict.

Ожидаемый код ошибки в теле ответа: BOOKING_ALREADY_CANCELLED.

Система обнаруживает, что бронирование уже находится в финальном состоянии CANCELLED, и отклоняет повторный запрос. Состояние бронирования и автомобиля не изменяется.

Тело ответа должно содержать:
{
  "code": "BOOKING_ALREADY_CANCELLED",
  "message": "<описание ошибки>"
}

Результат шага:

повторная отмена отклонена;
система вернула HTTP 409 с кодом ошибки BOOKING_ALREADY_CANCELLED;
статус бронирования по-прежнему CANCELLED;
статус автомобиля по-прежнему AVAILABLE.

5. Постусловия

После завершения сценария:

Бронирование {{bookingId}} существует в системе со статусом CANCELLED.
Автомобиль {{vehicleId}} имеет статус AVAILABLE и доступен для новых бронирований.
Попытка повторной отмены зафиксирована системой как ошибочная операция.

6. Бизнес-правила

Отмена бронирования допустима только в том случае, если текущий статус бронирования позволяет выполнить переход в состояние CANCELLED.
Повторная отмена уже отменённого бронирования запрещена.
При попытке повторной отмены система должна вернуть HTTP 409 с кодом ошибки BOOKING_ALREADY_CANCELLED.
Статус бронирования CANCELLED является финальным: из него не допускается никаких переходов через операцию отмены.
При отмене бронирования автомобиль переводится в статус AVAILABLE и остаётся в нём до создания нового бронирования.
Все операции выполняются через REST API с использованием JSON.
