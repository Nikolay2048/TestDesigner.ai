UC-007. Попытка создания бронирования заблокированным пользователем
Название сценария

Проверка отклонения запроса на создание бронирования, если инициирующий пользователь заблокирован в системе.

1. Бизнес-контекст

Система каршеринга поддерживает механизм блокировки пользователей. Заблокированный пользователь лишается права создавать новые бронирования. Система обязана проверять статус пользователя при каждом запросе на бронирование и отклонять запросы от заблокированных учётных записей до выполнения каких-либо иных проверок.

Данный сценарий проверяет, что система корректно идентифицирует заблокированного пользователя и возвращает соответствующую ошибку, не создавая бронирование и не изменяя статус автомобиля.

2. Участники сценария
Участник	Описание
Заблокированный пользователь	Пытается создать бронирование, несмотря на действующую блокировку учётной записи
API Gateway	Принимает REST-запросы и маршрутизирует их
Booking Service	Проверяет статус пользователя и отклоняет запрос при обнаружении блокировки
User Service	Предоставляет информацию о статусе учётной записи пользователя
Vehicle Service	Предоставляет список доступных автомобилей

3. Предусловия

Сервис доступен по REST API.
В системе существует как минимум один автомобиль со статусом AVAILABLE.
Пользователь с идентификатором "user-blocked" существует в системе и имеет статус BLOCKED.
Переменная {{startDate}} содержит корректную дату в будущем в формате ISO 8601.
Переменная {{city}} содержит наименование города для поиска доступных автомобилей.

4. Основной поток сценария

Шаг 1. Получение списка доступных автомобилей

Заблокированный пользователь инициирует запрос на получение доступных автомобилей в указанном городе.

Метод и URL: GET /v1/vehicles/available?city={{city}}

Ожидаемый HTTP-статус ответа: 200 OK.

Система возвращает список автомобилей со статусом AVAILABLE. Из полученного списка извлекается vehicleId первого автомобиля и сохраняется для использования в следующем шаге.

Примечание: получение списка автомобилей не требует авторизации и доступно даже заблокированным пользователям. Проверка статуса пользователя выполняется на этапе создания бронирования.

Результат шага:

переменная {{vehicleId}} содержит идентификатор доступного автомобиля;
автомобиль имеет статус AVAILABLE.

Шаг 2. Попытка создания бронирования от имени заблокированного пользователя

Заблокированный пользователь отправляет запрос на создание бронирования.

Метод и URL: POST /v1/bookings

Тело запроса:
{
  "userId": "user-blocked",
  "vehicleId": "{{vehicleId}}",
  "startDate": "{{startDate}}"
}

Важно: значение поля userId является литеральным — "user-blocked". Необходимо использовать именно эту конкретную строку, а не переменную {{user_id}}, которая может содержать идентификатор незаблокированного пользователя.

Ожидаемый HTTP-статус ответа: 403 Forbidden.

Ожидаемый код ошибки в теле ответа: USER_BLOCKED.

Система проверяет статус пользователя "user-blocked" и обнаруживает активную блокировку. Запрос на создание бронирования отклоняется. Проверка доступности автомобиля при этом не выполняется. Бронирование не создаётся, статус автомобиля не изменяется.

Тело ответа должно содержать:
{
  "code": "USER_BLOCKED",
  "message": "<описание ошибки>"
}

Результат шага:

запрос отклонён системой;
система вернула HTTP 403 с кодом ошибки USER_BLOCKED;
бронирование не создано;
статус автомобиля {{vehicleId}} остался AVAILABLE.

5. Постусловия

После завершения сценария:

Ни одно бронирование не было создано.
Автомобиль {{vehicleId}} сохраняет статус AVAILABLE и доступен для бронирования незаблокированными пользователями.
Учётная запись пользователя "user-blocked" по-прежнему заблокирована.
Система корректно обработала запрос от заблокированного пользователя и вернула информативное сообщение об ошибке.

6. Бизнес-правила

Система обязана проверять статус учётной записи пользователя при каждом запросе на создание бронирования.
Заблокированные пользователи не имеют права создавать бронирования.
Если пользователь заблокирован, система должна вернуть HTTP 403 с кодом ошибки USER_BLOCKED.
Проверка статуса пользователя выполняется до проверки доступности и существования автомобиля.
При отклонении запроса по причине блокировки пользователя статус автомобиля и прочие данные системы не изменяются.
Все операции выполняются через REST API с использованием JSON.
