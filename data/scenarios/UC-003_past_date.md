UC-003. Создание бронирования с датой в прошлом
Название сценария

Проверка отклонения запроса на бронирование автомобиля, если указанная дата начала бронирования находится в прошлом.

1. Бизнес-контекст

Система каршеринга требует, чтобы дата начала бронирования всегда была позже текущего серверного времени. Попытка создать бронирование с прошедшей датой является логически некорректной и должна быть отклонена на уровне валидации входных данных.

Данный сценарий проверяет, что система правильно выявляет некорректную дату и возвращает ошибку валидации, не создавая при этом никакого бронирования и не изменяя статус автомобиля.

2. Участники сценария
Участник	Описание
Пользователь	Намеренно или ошибочно указывает дату в прошлом при создании бронирования
API Gateway	Принимает REST-запросы клиента и маршрутизирует их
Booking Service	Выполняет валидацию даты бронирования и отклоняет некорректный запрос
Vehicle Service	Предоставляет информацию о доступных автомобилях

3. Предусловия

Сервис доступен по REST API.
В системе существует как минимум один автомобиль со статусом AVAILABLE.
Пользователь с идентификатором {{user_id}} существует в системе и не заблокирован.
Серверное время системы синхронизировано и является источником истины для проверки дат.
Переменная {{city}} содержит наименование города для поиска доступных автомобилей.

4. Основной поток сценария

Шаг 1. Получение списка доступных автомобилей

Пользователь выполняет запрос на получение доступных автомобилей в указанном городе.

Endpoint: GET /v1/vehicles/available

Ожидаемый HTTP-статус ответа: 200 OK.

Система возвращает список автомобилей со статусом AVAILABLE. Из полученного списка извлекается vehicleId первого автомобиля и сохраняется для использования в следующем шаге.

Результат шага:

переменная {{vehicleId}} содержит идентификатор доступного автомобиля;
автомобиль имеет статус AVAILABLE.

Шаг 2. Попытка создания бронирования с датой в прошлом

Пользователь отправляет запрос на бронирование выбранного автомобиля, указывая дату в прошлом.

Endpoint: POST /v1/bookings

Тело запроса:
{
  "userId": "{{user_id}}",
  "vehicleId": "{{vehicleId}}",
  "startDate": "2020-01-01T00:00:00Z"
}

Важно: значение поля startDate является литеральным — "2020-01-01T00:00:00Z". Необходимо использовать именно эту конкретную строку, а не переменную с будущей датой.

Ожидаемый HTTP-статус ответа: 400 Bad Request.

Ожидаемый код ошибки в теле ответа: START_DATE_MUST_BE_IN_FUTURE.

Система обнаруживает, что переданная дата находится в прошлом относительно текущего серверного времени, и отклоняет запрос на этапе валидации входных данных. Бронирование не создаётся, статус автомобиля не изменяется.

Тело ответа должно содержать:
{
  "code": "START_DATE_MUST_BE_IN_FUTURE",
  "message": "<описание ошибки>"
}

Результат шага:

запрос отклонён системой;
система вернула HTTP 400 с кодом ошибки START_DATE_MUST_BE_IN_FUTURE;
бронирование не создано.

5. Постусловия

После завершения сценария:

Ни одно бронирование для указанного автомобиля не было создано.
Автомобиль {{vehicleId}} сохраняет статус AVAILABLE.
Система корректно обработала ошибочный запрос и вернула информативное сообщение об ошибке.

6. Бизнес-правила

Дата начала бронирования должна строго превышать текущее серверное время.
Система обязана выполнять валидацию поля startDate при каждом запросе на создание бронирования.
Запросы с датой в прошлом должны быть отклонены с HTTP 400 и кодом ошибки START_DATE_MUST_BE_IN_FUTURE.
При отклонении запроса по причине некорректной даты статус автомобиля и данные системы не изменяются.
Серверное время является единственным источником истины для проверки временны́х условий.
Все операции выполняются через REST API с использованием JSON.
