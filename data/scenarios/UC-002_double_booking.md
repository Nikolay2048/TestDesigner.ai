UC-002. Попытка двойного бронирования одного автомобиля
Название сценария

Проверка защиты от одновременного бронирования одного и того же автомобиля двумя запросами подряд.

1. Бизнес-контекст

Система каршеринга допускает только одно активное бронирование на один автомобиль в каждый момент времени. Как только первое бронирование успешно создано и автомобиль переведён в статус BOOKED, любая повторная попытка забронировать тот же автомобиль должна быть отклонена.

Данный сценарий проверяет корректность работы механизма блокировки автомобиля: система не должна позволить создать второе бронирование для автомобиля, который уже занят.

2. Участники сценария
Участник	Описание
Пользователь	Инициирует две последовательные попытки бронирования одного автомобиля
API Gateway	Принимает REST-запросы клиента и маршрутизирует их
Booking Service	Управляет жизненным циклом бронирований, проверяет занятость автомобиля
Vehicle Service	Предоставляет и обновляет статус автомобиля

3. Предусловия

Сервис доступен по REST API.
В системе существует как минимум один автомобиль со статусом AVAILABLE.
Пользователь с идентификатором {{user_id}} существует в системе и не заблокирован.
Переменная {{startDate}} содержит корректную дату в будущем в формате ISO 8601.
Переменная {{city}} содержит наименование города для поиска доступных автомобилей.

4. Основной поток сценария

Шаг 1. Получение списка доступных автомобилей

Пользователь выполняет запрос на получение доступных автомобилей в указанном городе.

Метод и URL: GET /v1/vehicles/available?city={{city}}

Ожидаемый HTTP-статус ответа: 200 OK.

Система возвращает список автомобилей со статусом AVAILABLE. Из полученного списка извлекается vehicleId первого автомобиля и сохраняется для использования в последующих шагах.

Результат шага:

переменная {{vehicleId}} содержит идентификатор доступного автомобиля;
список содержит как минимум один элемент.

Шаг 2. Создание первого бронирования

Пользователь отправляет запрос на бронирование выбранного автомобиля.

Метод и URL: POST /v1/bookings

Тело запроса:
{
  "userId": "{{user_id}}",
  "vehicleId": "{{vehicleId}}",
  "startDate": "{{startDate}}"
}

Ожидаемый HTTP-статус ответа: 201 Created.

Система создаёт бронирование, генерирует уникальный bookingId, устанавливает статус CREATED и переводит автомобиль в состояние BOOKED.

Из тела ответа извлекается и сохраняется bookingId первого бронирования.

Результат шага:

создано первое бронирование;
переменная {{bookingId}} содержит идентификатор созданного бронирования;
статус бронирования — CREATED;
автомобиль {{vehicleId}} переведён в статус BOOKED.

Шаг 3. Попытка повторного бронирования того же автомобиля

Пользователь повторно отправляет запрос на бронирование того же автомобиля, который уже находится в статусе BOOKED.

Метод и URL: POST /v1/bookings

Тело запроса:
{
  "userId": "{{user_id}}",
  "vehicleId": "{{vehicleId}}",
  "startDate": "{{startDate}}"
}

Ожидаемый HTTP-статус ответа: 409 Conflict.

Ожидаемый код ошибки в теле ответа: VEHICLE_NOT_AVAILABLE.

Система обнаруживает, что автомобиль уже имеет активное бронирование, и отклоняет второй запрос. Никакого нового бронирования не создаётся.

Тело ответа должно содержать:
{
  "code": "VEHICLE_NOT_AVAILABLE",
  "message": "<описание ошибки>"
}

Результат шага:

второй запрос на бронирование отклонён;
система вернула HTTP 409 с кодом ошибки VEHICLE_NOT_AVAILABLE;
второе бронирование не создано.

5. Постусловия

После завершения сценария:

В системе существует ровно одно бронирование для автомобиля {{vehicleId}}.
Статус первого бронирования — CREATED.
Автомобиль {{vehicleId}} остаётся в статусе BOOKED.
Попытка двойного бронирования зафиксирована в системе как ошибочная операция.

6. Бизнес-правила

В каждый момент времени для одного автомобиля может существовать только одно активное бронирование.
Система обязана проверять статус автомобиля перед созданием нового бронирования.
Если автомобиль уже занят (статус BOOKED), система должна вернуть HTTP 409 с кодом ошибки VEHICLE_NOT_AVAILABLE.
Автомобиль не может быть забронирован повторно до тех пор, пока действующее бронирование не будет отменено или завершено.
Все операции выполняются через REST API с использованием JSON.
