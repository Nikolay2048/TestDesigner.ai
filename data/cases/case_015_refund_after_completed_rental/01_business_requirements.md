# Бизнес-требования. Возврат платежа после завершенной аренды

Сервис каршеринга должен поддерживать сценарий полного или частичного возврата платежа по завершенной аренде.

Документация описывает backend-поведение без UI. Все проверки должны выполняться на уровне backend API, БД, интеграций и асинхронных событий.

Система должна обеспечивать консистентность статусов пользователя, автомобиля, бронирования, аренды, платежей и связанных сущностей.

При ошибках бизнес-валидации backend должен возвращать единый код ошибки, определенный в ФЛК. Текст сообщения может отличаться между сервисами.

Операции, которые не прошли проверки, не должны изменять критичные данные в БД и не должны публиковать бизнес-события в Kafka.

События должны публиковаться через outbox-паттерн после успешной фиксации транзакции.

Недоступность Notification Service не должна откатывать основной бизнес-процесс.

Система должна сохранять audit trail для последующего анализа инцидентов, спорных ситуаций и финансовых сверок.

В постановках могут использоваться не полностью унифицированные термины. Для тест-дизайна следует сопоставлять их по смыслу с сущностями API и БД.
