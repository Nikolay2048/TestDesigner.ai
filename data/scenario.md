UC-001. Создание и отмена бронирования автомобиля
Название сценария

Создание бронирования автомобиля в системе каршеринга с последующей отменой бронирования.

1. Бизнес-контекст

Система каршеринга предоставляет пользователю возможность получить список доступных автомобилей, выбрать автомобиль и создать бронирование на определённое время.

Перед созданием бронирования система должна проверить доступность автомобиля и корректность входных данных. Дата начала бронирования должна находиться в будущем относительно текущего времени системы.

После успешного создания бронирования пользователь должен иметь возможность получить информацию о созданном бронировании и отменить его. После отмены статус бронирования должен измениться, а автомобиль должен снова стать доступным для бронирования другими пользователями.

2. Участники сценария
Участник	Описание
Пользователь	Инициирует операции поиска автомобиля и создания бронирования
API Gateway	Принимает REST-запросы клиента
Booking Service	Управляет жизненным циклом бронирований
Vehicle Service	Предоставляет информацию о доступности автомобилей
3. Предусловия
Сервис доступен по REST API.
В системе существуют автомобили со статусом AVAILABLE.
Пользователь с идентификатором user-1 существует в системе.
Сервис поддерживает операции:
получение доступных автомобилей;
создание бронирования;
получение информации о бронировании;
отмену бронирования.
Часы системы синхронизированы, и серверное время считается источником истины для проверки даты бронирования.
4. Основной поток сценария
Шаг 1. Получение списка доступных автомобилей

Пользователь инициирует запрос на получение списка доступных автомобилей.

Система обращается к сервису автомобилей и получает перечень автомобилей, которые могут быть забронированы в текущий момент времени.

В ответе система должна вернуть:

список автомобилей;
идентификатор автомобиля;
статус автомобиля;
базовую информацию об автомобиле.

Система должна отфильтровать автомобили со статусом AVAILABLE.

Из полученного списка должен быть выбран один автомобиль для дальнейшего бронирования.

Результат шага:

получен vehicleId доступного автомобиля;
выбран автомобиль для создания бронирования.
Шаг 2. Формирование данных бронирования

Клиентская сторона формирует запрос на создание бронирования.

В запросе должны присутствовать:

идентификатор пользователя;
идентификатор выбранного автомобиля;
дата начала бронирования.

Дата начала бронирования должна быть больше текущего времени системы.

Система подготавливает данные для передачи в сервис бронирования.

Результат шага:

сформирован валидный запрос на создание бронирования.
Шаг 3. Создание бронирования

Система принимает запрос на создание бронирования.

Во время обработки запроса система выполняет:

Проверку существования автомобиля.
Проверку доступности автомобиля.
Проверку корректности даты бронирования.
Проверку обязательных полей запроса.

Если проверки пройдены успешно:

создаётся новое бронирование;
генерируется уникальный идентификатор бронирования;
статус бронирования устанавливается в CREATED;
автомобиль помечается как занятый.

Система возвращает информацию о созданном бронировании.

Результат шага:

создано бронирование;
получен bookingId;
статус бронирования — CREATED.
Шаг 4. Получение информации о бронировании

После успешного создания бронирования пользователь инициирует запрос на получение информации по идентификатору бронирования.

Система должна:

найти бронирование;
вернуть данные бронирования;
вернуть текущий статус бронирования.

В ответе должны присутствовать:

bookingId;
vehicleId;
userId;
дата бронирования;
статус бронирования.

Результат шага:

подтверждено существование созданного бронирования;
подтвержден статус CREATED.
Шаг 5. Отмена бронирования

Пользователь инициирует отмену ранее созданного бронирования.

Система выполняет:

Проверку существования бронирования.
Проверку текущего статуса бронирования.
Проверку возможности отмены.

Если отмена допустима:

статус бронирования изменяется на CANCELLED;
автомобиль снова переводится в статус AVAILABLE.

Система возвращает обновлённое состояние бронирования.

Результат шага:

бронирование отменено;
статус изменён на CANCELLED;
автомобиль снова доступен для бронирования.
Шаг 6. Проверка итогового состояния бронирования

Пользователь повторно запрашивает информацию о бронировании.

Система возвращает актуальное состояние бронирования.

В ответе должен содержаться статус CANCELLED.

Результат шага:

подтверждено успешное завершение процесса отмены бронирования.
5. Постусловия

После завершения сценария:

Бронирование существует в системе.
Статус бронирования установлен в CANCELLED.
Автомобиль снова имеет статус AVAILABLE.
Идентификаторы vehicleId и bookingId могут использоваться в последующих запросах аудита или истории операций.
6. Бизнес-правила
Бронирование может быть создано только для автомобиля со статусом AVAILABLE.
Дата начала бронирования должна находиться в будущем.
Одновременно один автомобиль не может иметь несколько активных бронирований.
Повторная отмена уже отменённого бронирования запрещена.
При отмене бронирования автомобиль должен снова стать доступным.
Все операции выполняются через REST API с использованием JSON.
