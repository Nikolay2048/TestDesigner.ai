# Технические проблемы и ограничения

Этот документ честно описывает текущие ограничения системы: архитектурные, технические, связанные с LLM, и эксплуатационные. Понимание ограничений позволяет правильно оценить, когда система применима, а когда нет.

---

## 1. Ограничения Spec Parser

### 1.1 Нет поддержки cross-file $ref

**Проблема:** если OpenAPI-спека использует ссылки на другие файлы (`$ref: "./schemas/common.yaml#/components/schemas/Error"`), парсер падает с `ValueError`.

**Последствие:** нельзя использовать систему с многофайловыми OpenAPI проектами (реальные enterprise-проекты почти всегда многофайловые).

**Обходной путь:** вручную объединить спеки в один файл через `openapi-merge` или `swagger-merger`.

---

### 1.2 Не поддерживаются allOf/oneOf/anyOf

**Проблема:** `$ref: "#/components/schemas/BaseVehicle"` в сочетании с `allOf` не разворачивается корректно. Constraints из inherited-схем не попадают в `Endpoint.constraints`.

**Последствие:** для polymorphic schemas граничные значения могут не генерироваться.

---

### 1.3 Constraints только плоские (не вложенные)

**Проблема:** Spec Parser собирает constraints по имени поля, без учёта пути. Если два разных объекта имеют поле `amount` с разными ограничениями — в constraints окажется только последнее.

**Последствие:** Test Designer может применить неправильные границы для поля с дублирующимся именем.

---

### 1.4 Не поддерживается авторизация (Security Schemes)

**Проблема:** `securitySchemes` из OpenAPI (Bearer, OAuth2, API Key) не извлекаются и не применяются автоматически.

**Последствие:** если сервис требует авторизации — нужно вручную передавать токен через `env_vars` и вручную прописывать header в биндингах.

---

## 2. Ограничения Scenario Analyst (LLM)

### 2.1 Качество зависит от качества постановки

**Проблема:** Scenario Analyst воспринимает текст как источник истины. Если постановка неточная, противоречивая или неполная — FlowCard будет ошибочным.

**Конкретные случаи:**
- Постановка не указывает явно, какой параметр берётся из какого ответа → LLM угадывает
- Нет явного указания порядка операций → LLM может перепутать порядок
- Постановка упоминает поле не тем именем, что в спеке → биндинг сломан

**Нет автоматического исправления.** Validator поймает синтаксические ошибки (несуществующий step_id), но семантические (неправильный JSONPath) — нет.

---

### 2.2 Локальная 14B-модель ненадёжна для complex structured output

**Проблема:** `qwen2.5:14b-instruct` плохо держит строгий структурированный вывод при сложных промптах. Особенно проблемно:
- Длинные списки VariableBinding (5+ биндингов) — модель начинает галлюцинировать поля
- Вложенные Pydantic-модели — модель путает вложенность
- Точные JSONPath-выражения — модель пишет нестандартный синтаксис

**Последствие:** retry-циклы срабатывают часто на локальной модели. На Claude/GPT-4 проблема значительно меньше.

---

### 2.3 Нет memory между прогонами

**Проблема:** каждый запуск Scenario Analyst начинается с нуля. Если сценарий уже анализировался и FlowCard был хорошим — в следующем прогоне это не учитывается.

**Последствие:** нет механизма «запомнить хороший FlowCard и использовать как baseline».

---

## 3. Ограничения Executor

### 3.1 Тесты не идемпотентны без teardown

**Проблема:** FlowCard.teardown_steps определён в модели, но Executor его не выполняет. После прогона UC_003 (подтверждение бронирования) авто остаётся заблокированным. Следующий прогон UC_001 может не найти доступных авто.

**Последствие:** повторный прогон на реальном сервисе даёт другой результат. На mock-сервере решается через `/api/v1/mock/reset`.

---

### 3.2 Нет поддержки сложных JSONPath

**Проблема:** `resolve_jsonpath()` поддерживает только: `$.field`, `$.arr[N].field`, `$.arr[*].field`. Не поддерживается:
- Фильтры: `$.items[?(@.status=="active")]`
- Рекурсивный спуск: `$..carId`
- Множественные индексы: `$.items[0,1]`

**Последствие:** если ответ сервера имеет нестандартную вложенность, Scenario Analyst должен сформулировать JSONPath в рамках поддерживаемого подмножества.

---

### 3.3 Нет передачи заголовков (Headers)

**Проблема:** `build_request()` формирует только query_params и body. HTTP-заголовки (Authorization, Content-Type, X-Request-ID) не передаются.

**Последствие:** если endpoint требует кастомные заголовки — нужно ручное изменение кода.

---

### 3.4 Лимит попыток стабилизации может быть недостаточным

**Проблема:** `MAX_STEP_ATTEMPTS=3`, `MAX_TOTAL_FIXES=9`. Для сложных сценариев с 5+ шагами этого может не хватить.

**Последствие:** сценарий помечается как `is_stabilized=False`, и система останавливается.

---

### 3.5 Mock-сервер не покрывает все edge cases

**Проблема:** `mock/api.py` реализует основную бизнес-логику UC_001–008, но:
- Не реализует все 400/422 кейсы (некоторые возвращают 500 вместо 400)
- TTL чернового бронирования не проверяется по реальному времени (упрощено)
- Авторизация — stub (принимает любой токен)

**Последствие:** негативные кейсы на mock могут давать другой статус, чем на реальном сервисе.

---

## 4. Ограничения Test Designer

### 4.1 LLM-кейсы могут дублироваться

**Проблема:** equivalence и negative вызываются отдельно, но могут генерировать похожие кейсы (например, несуществующий carId может попасть и в equivalence, и в negative).

**Нет дедупликации.** Система не проверяет, что кейсы уникальны по содержанию.

---

### 4.2 State-based кейсы не всегда реалистичны

**Проблема:** LLM генерирует `setup_step_ids` для state_based кейсов. Иногда модель указывает шаги, которые технически невозможно пропустить (интегральные предусловия), или пропускает шаги, необходимые для создания FK-зависимостей.

**Последствие:** часть state_based кейсов при прогоне падает не по ожидаемой причине.

---

### 4.3 Нет техники Pairwise

**Проблема:** для endpoints с 3+ независимыми параметрами не генерируются комбинаторные кейсы.

**Последствие:** некоторые комбинации параметров остаются непокрытыми.

---

### 4.4 Boundary кейсы только для числовых и строковых constraints

**Проблема:** `_generate_boundary()` обрабатывает `enum`, `minimum`, `maximum`, `minLength`, `maxLength`. Не обрабатывает:
- `pattern` (regex)
- `format` (date, email, uuid)
- `multipleOf`
- `uniqueItems` для массивов

---

## 5. Ограничения Collection Builder

### 5.1 JS pre-request scripts — только 4 генератора

**Проблема:** `_gen_prerequest()` генерирует JS только для `future_datetime`, `future_datetime_end`, `decimal_amount`, `uuid4`. Любой новый генератор требует изменения кода.

---

### 5.2 Нет проверки тела ответа в test scripts

**Проблема:** test scripts проверяют только статус-код. Структура тела ответа не валидируется.

**Последствие:** коллекция может «зелениться» в Postman, даже если тело ответа неправильное.

---

### 5.3 Одна коллекция — один сценарий

**Проблема:** при запуске нескольких сценариев система записывает отдельные файлы коллекций, а не один объединённый.

**Последствие:** QA-инженеру нужно импортировать несколько коллекций.

---

## 6. Ограничения диагностики

### 6.1 Diagnosis — гипотеза, не приговор

**Проблема:** система явно указывает, что диагноз — это гипотеза (`confidence: 0.0–1.0`), но это требует от пользователей понимания. На практике есть риск воспринять `SUSPECTED_SERVICE_BUG` как окончательный вердикт.

**Меры:** `needs_human=True` форсируется для всех service_bug и low-confidence кейсов. Но человек всё равно должен принять финальное решение.

---

### 6.2 Layer 1 не покрывает семантические ограничения

**Проблема:** Layer 1 (jsonschema) проверяет только структурные ограничения. Бизнес-правила типа «дата начала не может быть в прошлом» или «endDate должна быть после startDate» не проверяются автоматически.

**Последствие:** ошибки, связанные с семантическими ограничениями, попадают в Layer 2 (LLM), который может неправильно их классифицировать.

---

## 7. Операционные ограничения

### 7.1 Нет персистентного хранения состояния

**Проблема:** все данные (FlowCard, TestCase, ExecResult) существуют только в памяти во время прогона. После завершения — только JSON-файлы в `output/`.

**Последствие:** нет истории прогонов, нет трендов, нет сравнения результатов между версиями.

---

### 7.2 Нет параллельного прогона сценариев

**Проблема:** несколько UC прогоняются последовательно. На 8 UC с реальным сервисом прогон занимает 5–15 минут (в зависимости от LLM и latency сервиса).

---

### 7.3 Нет CI/CD интеграции

**Проблема:** система запускается вручную через `python src/main.py`. Нет готового Docker-образа, нет GitHub Actions workflow, нет webhook для запуска по событию.

---

### 7.4 Качество сильно зависит от модели

**Проблема:** на qwen2.5:14b-instruct:
- Scenario Analyst требует 2–3 retry на сложных сценариях
- Test Designer генерирует дублирующиеся LLM-кейсы
- Stabilizer иногда предлагает невалидные фиксы

На Claude Sonnet 4.6 / GPT-4o качество значительно выше, но стоимость растёт.

---

## 8. Что система не умеет делать принципиально

| Функциональность | Причина невозможности |
|---|---|
| Тестирование WebSocket / gRPC | Архитектурно не заложено, только REST |
| Асинхронные флоу (polling) | Нет механизма ожидания и повторных запросов |
| Генерация нагрузочных тестов | Нет сбора метрик производительности |
| Автоматическая OAuth2 авторизация | Нет flow code/implicit, только Bearer token |
| Работа без спецификации | LLM не может надёжно инверсировать спеку из кода |
| Полностью автономное исполнение | Подозрение на баг → обязательно нужен человек |
