# TestDesignerAI — Концепция системы

## Что такое TestDesignerAI

TestDesignerAI — система автоматического тест-дизайна и генерации интеграционных тестов для REST API. Она принимает на вход текстовые описания сценариев поведения микросервисов и OpenAPI-спецификации, а на выходе производит полноценный тест-дизайн, прогоняет сценарии на реальном сервере и экспортирует результат в Postman-коллекцию, готовую к импорту.

Система решает конкретную проблему: написание тест-кейсов для REST API — монотонная и трудоёмкая работа, требующая одновременно знания бизнес-логики, понимания спецификации и владения техниками тест-дизайна. Большая часть этой работы формальна и воспроизводима — именно её автоматизирует система.

---

## Что система принимает на вход

### 1. Сценарии использования (Use Case)

Текстовые описания (Markdown) последовательностей действий в системе с точки зрения пользователя или системного аналитика. Каждый UC описывает:
- предусловия (что должно быть выполнено до начала сценария)
- основной поток (последовательность вызовов API)
- альтернативные потоки (ошибочные пути)
- постусловия (что изменилось в системе)

Пример (аренда автомобиля):
```
UC_001: Поиск доступных автомобилей
Актор: клиент
Предусловие: клиент зарегистрирован и авторизован
Основной поток:
  1. Клиент указывает город, дату начала и конца аренды, класс автомобиля
  2. Система возвращает список доступных автомобилей с ценой
Результат: получен carId, searchSessionId
```

### 2. OpenAPI/Swagger-спецификации

YAML/JSON-файлы, описывающие:
- endpoints (method, path, параметры)
- схемы запросов/ответов (JSON Schema)
- коды ответов (200, 201, 400, 404, 422, …)
- ограничения (enum, minimum, maximum, minLength, maxLength, required)

### 3. Конфигурация окружения

- `base_url` — адрес тестируемого сервиса (или mock-сервера)
- `env_vars` — seed-переменные: токены, идентификаторы существующих объектов

## Что система выдаёт на выходе

### 1. Стабилизированная карточка потока (FlowCard)

Машиночитаемое описание happy-path сценария. Содержит:
- упорядоченные шаги (step_id, operation_id)
- для каждого шага: откуда берётся каждый параметр (VariableBinding)
  - GENERATED — генерируется автоматически (UUID, дата, сумма)
  - FROM_STEP — извлекается из ответа предыдущего шага (JSONPath)
  - STATIC — константа из постановки
  - ENV — из конфигурации окружения
- что шаг «производит» (какие поля нужны следующим шагам)
- лог стабилизации (какие изменения потребовались, чтобы сценарий прошёл)

### 2. Набор тест-кейсов (TestCase[])

Сгенерированные кейсы по шести техникам тест-дизайна:

| Техника | Источник | Описание |
|---------|----------|----------|
| Happy Path | Код | 1 кейс — сквозной сценарий без отклонений |
| Boundary | Код | Граничные значения из constraints спеки |
| Negative (missing field) | Код | Удаление каждого required-поля по одному |
| Equivalence | LLM | Семантические классы эквивалентности из постановки |
| Negative (semantic) | LLM | Бизнес-нарушения: несуществующие ID, конфликты |
| State Based | LLM | Нарушения порядка шагов |

Каждый кейс содержит:
- setup_chain — предварительные шаги (предусловия)
- modified_inputs — мутации данных
- expected_status — ожидаемый HTTP-статус
- assertions — проверки ответа

### 3. Postman-коллекция (JSON)

Готовый артефакт для импорта в Postman. Структура:

```
Collection
└── [flow_id] Название сценария
    ├── Happy Path
    │   └── [happy_path] Название кейса
    │       ├── [setup] step_01 — searchCars
    │       └── [target] confirmBooking
    ├── Boundary
    │   ├── [boundary] cityId not in enum
    │   └── [boundary] driverAge below minimum
    ├── Negative
    ├── Equivalence
    └── State Based
```

Особенности коллекции:
- Pre-request scripts (JavaScript) — генерация UUID, дат, сумм
- Test scripts — ассерты на статус-коды, извлечение переменных между запросами
- Variables — `baseUrl`, `customerId` и другие seed-значения
- Переменные передаются через `pm.environment.set/get` — каждый шаг пишет, следующий читает

### 4. Метрики покрытия

- Сколько endpoints покрыто тест-кейсами (в %)
- Разбивка по техникам (сколько кейсов каждой техники)
- Результаты прогона Phase 2 (passed/failed, pass_rate)
- Диагностика падений (категории причин)

### 5. Диагностика падений

Когда сценарий не проходит при стабилизации, система классифицирует причину:
- `TEST_DATA_ISSUE` — данные нарушали JSON Schema (неправильный enum, выход за границы)
- `SPEC_GAP` — данные валидны по схеме, но нарушают бизнес-правила из постановки
- `CARD_ERROR` — Scenario Analyst ошибся в зависимостях/биндинге
- `SUSPECTED_SERVICE_BUG` — данные валидны и по схеме, и по постановке, но сервер отверг
- `UNCERTAIN` — недостаточно информации для вывода

## Как это работает: архитектура

### Ключевой принцип: код ведёт состояние, LLM решает узкие задачи понимания

LLM используется **только** там, где нужно понимание текста:
- Какие операции вызвать и в каком порядке (Scenario Analyst)
- Откуда берётся каждый параметр шага (Scenario Analyst, Phase 2)
- Предложить фикс при падении шага (Stabilizer)
- Классифицировать причину падения (Diagnosis Layer 2)
- Сгенерировать кейсы по семантическим техникам (Test Designer)

Всё остальное — детерминированный Python: парсинг спецификации, подстановка переменных, HTTP-запросы, сборка Postman JSON, граничные значения, метрики.

Примерное соотношение: **60% детерминированный код, 40% LLM**.

### Принцип «много узких агентов вместо одного умного»

Каждый LLM-вызов — одна задача с чётким структурированным выходом (Pydantic через `with_structured_output`). Это критично для локальной 14B-модели, которая плохо справляется со свободным рассуждением.

Пример: Test Designer делает 3 отдельных LLM-вызова для equivalence, negative (semantic) и state_based — не один вызов «придумай все тесты».

### Принцип «инварианты безопасности в коде, не в промпте»

После каждого LLM-вызова Python проверяет и форсирует инварианты:
- Все operation_id из ответа LLM реально существуют в endpoints
- Все step_id из ответа LLM совпадают с шагами флоу
- Нельзя перезаписать FROM_STEP/ENV биндинги в обычных кейсах
- Если данные были валидны, а сервер отверг → `needs_human=True` принудительно

### Граф LangGraph

```
[Spec Parser]          (CODE)
        ↓ endpoints[]
[Scenario Analyst]     (LLM × 2)
        ↓ FlowCard
[Validator]            (CODE)
        ↓ validation_errors[]
[Executor Stabilize]   (CODE + LLM stabilizer)
        ↓
    ┌── is_stabilized=False → [Reporter] → END
    └── is_stabilized=True  → [Diagnosis] (CODE + LLM)
                                    ↓
                             [Test Designer]  (CODE + LLM × 3)
                                    ↓ test_cases[]
                             [Executor Run All] (CODE)
                                    ↓ exec_results[]
                             [Collection Builder] (CODE)
                                    ↓ postman_collection.json
                             [Reporter]  (CODE)
                                    ↓ metrics + report
```

## Эталонный сценарий: аренда автомобиля (UC_001–UC_008)

Восемь UC покрывают полный жизненный цикл аренды автомобиля:

| UC | Название | Ключевые данные |
|----|----------|-----------------|
| UC_001 | Поиск доступных авто | → carId, searchSessionId |
| UC_002 | Создание черновика бронирования | carId → reservationDraftId, price |
| UC_003 | Подтверждение бронирования | reservationDraftId → confirmedBookingId |
| UC_004 | Начало аренды | confirmedBookingId → rentalId |
| UC_005 | Продление аренды | rentalId → новый срок |
| UC_006 | Создание отчёта о нарушениях | rentalId → reportId |
| UC_007 | Завершение аренды | rentalId → итоговая стоимость |
| UC_008 | Отмена бронирования | confirmedBookingId → статус отмены |

Ключевые зависимости между UC:
- UC_002 требует carId из UC_001
- UC_003 требует reservationDraftId из UC_002
- UC_004 требует confirmedBookingId из UC_003
- UC_007 требует rentalId из UC_004

Это делает сценарий идеальным стресс-тестом для системы: глубокая цепочка зависимостей, состояния, которые меняются (авто заблокировано после UC_003), необходимость teardown.

## Что система сознательно НЕ делает

- Не генерирует нагрузочные тесты
- Не работает с WebSocket, gRPC, GraphQL — только REST
- Не поддерживает асинхронные флоу (polling, callback) — только синхронные вызовы
- Не управляет тестовой базой данных — работает с mock-сервером или реальным сервисом
- Не обрабатывает OAuth/JWT автоматически — токены задаются через env_vars вручную
- Не заменяет аналитика: постановки должны быть написаны человеком
- Не исполняет Postman-коллекцию через Newman — это только экспортный артефакт
