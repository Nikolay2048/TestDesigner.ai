## 1. Что мы строим

Система, которая на входе принимает:
- текстовые **постановки** (use-case сценарии поведения микросервисов на REST API);
- **OpenAPI/Swagger** спецификации (возможно несколько файлов со ссылками `$ref` между собой);
- вспомогательную документацию.

На выходе даёт:
- полный **тест-дизайн**: тест-кейсы, сгруппированные, с применением техник тест-дизайна;
- **оценку покрытия** и метрики (сколько сценариев покрыто, сколько кейсов, сколько endpoints, незатронутые endpoints и т.д.);
- готовую **Postman-коллекцию** с генерацией данных и проверками (как ВЫХОДНОЙ АРТЕФАКТ).

Только REST API.

## 2. Стек

- **Python**
- **LangGraph** — оркестрация (граф состояний с узлами, условными рёбрами, циклами).
- **LangChain** — для LLM-вызовов, `with_structured_output` для строгого вывода.
- **Pydantic** — все модели данных строго типизированы.
- **jsonschema** — валидация данных по схемам из спеки.
- **requests** — HTTP-запросы исполнителя.
- **Локальная модель для отладки:** `qwen2.5:14b-instruct` (через Ollama).
  Финальное качество агентов проверяется на сильной модели.
  Выбор модели держать за ОДНОЙ переменной/конфигом, чтобы переключать одной строкой.

## 3. ГЛАВНЫЕ ПРИНЦИПЫ (нарушать нельзя)

### 3.1. Код держит состояние и факты, LLM решает узкие задачи понимания
LLM используется ТОЛЬКО там, где нужно понимание текста. Всё, что можно посчитать
детерминированно (парсинг спеки, подстановка переменных, сборка Postman JSON, метрики,
валидация по JSON Schema) — делает обычный Python-код, НЕ агент.
Ориентир: ~60% системы — детерминированный код, ~40% — LLM-агенты.

### 3.2. Много узких узлов вместо одного «умного» агента
Никаких гигантских промптов «сделай всё». Каждый агент — одна чёткая задача,
строгий вход, строгий выход (Pydantic через `with_structured_output`).
Это критично ещё и потому, что локальная 14B-модель плохо тянет свободное рассуждение.

### 3.3. Executor сам шлёт HTTP-запросы. Postman НЕ движок исполнения.
Исполнение и стабилизация — это Python (`requests`), вживую, без Newman.
Postman-коллекция — это ФИНАЛЬНЫЙ ЭКСПОРТ результата, артефакт для человека.
Сама система свою коллекцию не исполняет.

### 3.4. Executor: код ведёт цикл по шагам, агент зовётся точечно
НЕ давать агенту свободный ReAct-цикл «пройди весь сценарий сам».
Код-оркестратор идёт по шагам карточки:
подставляет переменные → шлёт запрос → проверяет статус/ассерты → извлекает поля в контекст.
Агент вызывается ТОЛЬКО когда шаг упал — на узкую задачу «предложи фикс данных».
Контекст переменных (carId, bookingId, сгенерированные даты) ведёт КОД, не агент.

### 3.5. Инварианты безопасности живут в коде, а не в промпте
Промпт — это просьба, код — это гарантия. Критичные правила (например
«подозрение на баг сервиса → всегда к человеку») дублируются Python-проверкой
ПОСЛЕ ответа LLM. Никогда не полагаться только на то, что модель послушается промпт.

### 3.6. Никаких выдумок
Имена полей, границы, коды ответов — брать из OpenAPI-спеки, не выдумывать.
Если данных не хватает для вывода — агент обязан вернуть `UNCERTAIN`, а не угадывать.

## 4. Архитектура: поток узлов графа

```
[Spec Parser] (КОД)
   → endpoints[]
[Scenario Analyst] (АГЕНТ)
   → flow_card (шаги, bindings переменных, зависимости, requires_flows)
[Validator] (КОД)  ← дешёвый, критичный: ловит галлюцинации статически
   → проверка графа: все FROM_* имеют источник, нет циклов, поля есть в схемах
[Executor — фаза 1: стабилизация happy-path] (КОД-оркестратор + АГЕНТ-стабилизатор)
   → стабилизированная карточка + лог изменений
   (если не прошёл за N попыток → стоп, отчёт «сценарий не проходит»)
[Diagnosis] (АГЕНТ, ОДНОПРОХОДНЫЙ, без петли)
   → гипотезы о природе падений (НЕ приговор) + confidence + evidence
[Human Review] (LangGraph interrupt)
   → человек аппрувит / переклассифицирует / правит карточку
[Test Designer] (АГЕНТ)
   → размножает кейсы от УЖЕ рабочей карточки (техники тест-дизайна)
[Executor — фаза 2: прогон всех кейсов] (КОД + АГЕНТ при падениях)
   → результаты по каждому кейсу (для негативных «успех» = ожидаемая ошибка)
[Collection Builder] (КОД + чуть LLM для сниппетов)
   → Postman collection (экспортный артефакт)
[Reporter] (КОД)
   → метрики + отчёт для человека
```

**Data Generator — НЕ узел линии, а СЕРВИС/инструмент**, которым пользуется Executor.
Стоит сбоку.

### Почему именно такой порядок (частые ошибки)
- Test Designer ПОСЛЕ стабилизации happy-path: пока сквозной сценарий не проходит,
  нет смысла плодить от него негативы.
- Исполнение разбито на 2 фазы: фаза 1 — довести happy-path до зелёного;
  фаза 2 — прогнать все размноженные кейсы.
- НЕТ петли Executor↔Analyst. Executor производит ФАКТЫ, Diagnosis — ГИПОТЕЗЫ,
  человек — ВЕРДИКТ. Каждый делает то, что умеет надёжно.
- Spec Parser ничего «не решает» (разбивать/не разбивать) — всегда нормализует
  всё в единый плоский список endpoints со схемами. Скучный и предсказуемый.

## 5. Модели данных (Pydantic) — это контракты между узлами

```python
from enum import Enum
from pydantic import BaseModel

# ---------- Spec Parser output ----------
class Endpoint(BaseModel):
    operation_id: str            # уникальный id операции
    method: str                  # "POST"
    path: str                    # "/cars/search"
    path_params: list[dict]
    query_params: list[dict]
    request_schema: dict | None  # JSON Schema тела
    response_schemas: dict       # {"200": schema, "400": schema, ...}
    required_fields: list[str]
    constraints: dict            # извлечённые границы: {"city": {"minLength": 1}}

# ---------- Происхождение переменной (provenance) ----------
class VarSource(str, Enum):
    GENERATED = "generated"      # рождается в шаге (faker/uuid/даты)
    FROM_STEP = "from_step"      # из ответа предыдущего шага этого же потока
    FROM_FLOW = "from_flow"      # из выполненного сценария-предусловия
    STATIC = "static"            # константа
    ENV = "env"                  # из окружения (baseUrl, токен)

class VariableBinding(BaseModel):
    name: str
    source: VarSource
    generator: str | None = None      # имя функции из словаря Data Generator
    source_ref: str | None = None     # step_id или flow_id.step_id
    source_field: str | None = None   # JSONPath: "$.cars[0].carId"
    value: str | None = None
    target_location: str | None = None  # "body.carId" / "path.id" / "query.city"

# ---------- Сценарий / Поток ----------
class ScenarioStep(BaseModel):
    step_id: str
    operation_id: str            # ссылка на Endpoint
    inputs: list[VariableBinding]
    produces: list[str]          # JSONPath полей, которые шаг отдаёт наружу
    depends_on: list[str] = []   # step_id предусловий внутри потока

class FlowCard(BaseModel):
    flow_id: str
    name: str
    description: str
    requires_flows: list[str] = []      # сценарии-предусловия (inter-flow)
    steps: list[ScenarioStep]
    exports: list[str] = []
    teardown_steps: list[ScenarioStep] = []
    is_stabilized: bool = False
    stabilization_log: list[dict] = []

# ---------- Тест-кейсы (после Test Designer) ----------
class TestTechnique(str, Enum):
    HAPPY_PATH = "happy_path"
    EQUIVALENCE = "equivalence"
    BOUNDARY = "boundary"
    NEGATIVE = "negative"
    STATE_BASED = "state_based"

class TestCase(BaseModel):
    case_id: str
    flow_id: str
    technique: TestTechnique
    title: str
    target_step: str
    setup_chain: list[ScenarioStep]      # развёрнутые предусловия (строит КОД)
    modified_inputs: list[VariableBinding]
    expected_status: int
    assertions: list[dict]
    group: str                           # для метрик: flow/endpoint/technique

# ---------- Diagnosis (после стабилизации) ----------
class DiagnosisCategory(str, Enum):
    TEST_DATA_ISSUE = "test_data_issue"      # данные не соответствовали спеке/постановке
    SPEC_GAP = "spec_gap"                     # спека неполна/противоречит постановке
    SCENARIO_CARD_ERROR = "card_error"        # Analyst ошибся в зависимости/binding
    SUSPECTED_SERVICE_BUG = "service_bug"      # данные валидны, сервис всё равно отверг
    UNCERTAIN = "uncertain"                    # не хватает информации

class Diagnosis(BaseModel):
    case_id: str
    step_id: str
    what_changed: dict
    category: DiagnosisCategory   # ГИПОТЕЗА, не приговор
    confidence: float             # 0.0–1.0
    evidence: list[str]
    reasoning: str
    needs_human: bool
    human_decision: str | None = None

# ---------- Executor output ----------
class ExecResult(BaseModel):
    case_id: str
    passed: bool                  # для негативного passed = получили ожидаемую ошибку
    steps_log: list[dict]
    stabilization_applied: list[dict] = []
    failure_reason: str | None = None

# ---------- Data Generator ----------
class GenFunction(BaseModel):
    name: str
    description: str
    params_schema: dict
    python_impl: str             # исполняемый Python (для Executor вживую)
    postman_snippet: str         # JS для pre-request (для экспортной коллекции)
    status: str                  # "approved" | "pending_review"
    examples: list

class GenRequest(BaseModel):
    field_name: str
    constraints: dict
    context: str

class GenResponse(BaseModel):
    value: object
    function_used: str
    policy: str                  # человекочитаемое объяснение, как получено значение
    is_new_function: bool        # True → ушло на ревью человеку
```

## 6. Два механизма связывания данных (не путать!)

**Случай 1 — между сценариями (inter-flow):** чтобы тестировать B, надо целиком
прогнать сценарий-предусловие A. Решается полем `requires_flows` + РАЗВОРАЧИВАНИЕМ
(flattening) через топологическую сортировку. Делает КОД, не LLM. Шаги A в составе
теста B — это setup с минимальными ассертами «выполнилось», а не полный тест A.

**Случай 2 — внутри сценария (intra-flow):** часть переменных GENERATED (рождаются
в шаге), часть FROM_STEP/FROM_FLOW (извлекаются из ответов). Закрывается полем
`source` в `VariableBinding`.
ВАЖНО: генерируй значение ОДИН раз и переиспользуй. Если дата нужна в шаге 1 и шаге 3
одинаковой — она GENERATED в шаге 1 и FROM_STEP в шаге 3, НЕ генерируется заново.

## 7. Техники тест-дизайна (содержание Test Designer)

- **Эквивалентное разбиение** — классы валидный/невалидный/граничный, по представителю.
- **Граничные значения** — на границах из спеки (minLength/max/enum). Брать из `constraints`.
- **Негативное** — нет required-поля, неверный тип, битый JSON, невалидная авторизация,
  чужие/несуществующие ID.
- **На основе состояний** — нарушенный порядок (GET до POST, двойное удаление/подтверждение).
- **Pairwise** — когда у endpoint много независимых параметров.
- **По кодам ответов** — на каждый документированный код (200/400/401/404/422) свой кейс.

Прогонять техники ОТДЕЛЬНЫМИ вызовами LLM (один проход — одна техника), не «придумай тесты».
Группировать кейсы: сценарий → endpoint → техника (это даёт чистые метрики).

## 8. Логика Diagnosis (как отличить плохие данные от бага сервиса)

Два слоя:
- **Слой 1 (КОД, jsonschema):** прошли ли исходные данные JSON Schema endpoint'а?
  - НЕТ → честная стабилизация плохих данных (TEST_DATA_ISSUE/CARD_ERROR).
  - ДА, но сервер отверг → КРАСНАЯ ЗОНА, нужен слой 2.
- **Слой 2 (LLM):** валидны ли данные семантически по постановке?
  - Нарушают явное ограничение постановки (которого нет в схеме) → SPEC_GAP.
  - Валидны и по схеме, и по постановке, а сервер отверг → SUSPECTED_SERVICE_BUG.
  - Не хватает данных → UNCERTAIN.

**Жёсткое правило (КОД, после LLM):** если «помогла» подмена данных, которые были
ВАЛИДНЫ по спеке → это не стабилизация, а подозрение на баг. needs_human=True
принудительно, статус «passed_with_suspicion», НЕ красить в зелёный.
Лучше переосторожничать и позвать человека зря, чем спрятать баг.

Промпт Diagnosis обязан: давать явный выход в UNCERTAIN; требовать evidence ДО вывода;
запрещать домысливать ограничения, которых нет в постановке; привязывать confidence
к наличию прямой цитаты. Постобработка кодом форсит: service_bug → human;
confidence<0.6 → human; вывод без evidence → понизить и к человеку.

## 9. Data Generator (human-in-the-loop)

- На `GenRequest` ищет approved-функцию по типу/формату/имени. Нашёл — генерит,
  возвращает значение + политику.
- Не нашёл — LLM пишет новую `GenFunction` (И python_impl, И postman_snippet),
  помечает `pending_review`, использует её СРАЗУ (не блокировать Executor),
  ставит `is_new_function=True`.
- Человек ревьюит pending → переводит в approved (через LangGraph interrupt).
  Словарь насыщается, со временем новых функций пишется меньше.
- Хранилище: на старте JSON-файл, позже SQLite. Не усложнять БД раньше времени.
- БЕЗОПАСНОСТЬ: сгенерированный Python проверять в песочнице, try/except,
  ограничивать импорты. LLM может написать ошибочный/опасный код.

## 10. Состояние/нюансы исполнения

- Сквозные сценарии МЕНЯЮТ состояние системы (после подтверждения авто заблокировано).
  Тесты не идемпотентны. Решения: свежие данные на каждый прогон ИЛИ teardown_steps
  (отмена бронирования в конце). Заложить `teardown_steps` в модель сразу.
- Нарушенный порядок шагов — это ЦЕННЫЙ негативный кейс (state_based), не баг теста.
- В Executor: setup-шаги (предусловия) при падении → чинить ИСТОЧНИК, не целевой шаг.
  Не анализировать падение шага, у которого провалился setup.
- Лимит попыток стабилизации обязателен (например 3–5 на шаг, ~15 на сценарий).
  Иначе бесконечный цикл.

## 11. ПЛАН ЭТАПОВ — делать СТРОГО по одному, не прыгать

- **Этап 0 — каркас.** State (TypedDict) + Pydantic-модели + пустой граф LangGraph
  со ВСЕМИ узлами-заглушками. Прогнать состояние насквозь. БЕЗ LLM. Цель — увидеть поток.
- **Этап 1 — Spec Parser.** Реальный парсинг ОДНОЙ простой OpenAPI: резолв `$ref`
  (в т.ч. между файлами), извлечение endpoints, схем, границ в `constraints`.
  Покрыть тестами — это фундамент.
- **Этап 2 — Collection Builder на захардкоженном шаге.** Собрать ВАЛИДНУЮ Postman-
  коллекцию из одного шага, импортнуть в Postman, убедиться что работает.
  (Раньше дизайнера — чтобы рано увидеть осязаемый результат на выходе.)
- **Этап 3 — Scenario Analyst** на одном простом сценарии. `with_structured_output`
  → валидный FlowCard. Первый настоящий LLM-узел.
- **Этап 4 — Executor: один шаг кодом.** Подстановка переменных → execute → проверка.
  БЕЗ агента. Потом второй шаг с передачей carId через контекст (код ведёт контекст).
- **Этап 5 — Агент-стабилизатор** в точку «шаг упал», узкая задача фикса. Лимит попыток.
- **Этап 6 — Diagnosis** (слой код + слой LLM) + правило «валидные данные → подозрение».
- **Этап 7 — Test Designer** — размножение кейсов по техникам.
- **Этап 8 — inter-flow композиция** (requires_flows + flattening). ТОЛЬКО после того
  как один поток гоняется зелёным.
- **Этап 9 — Reporter и метрики.**

К концу этапа 2–3 должен быть работающий вертикальный срез (один endpoint → коллекция).
Система на каждом этапе остаётся ЗАПУСКАЕМОЙ: заглушки заменяются по одной.

## 12. Как Claude Code должен работать в этом проекте

- **Бери ОДИН узел/этап из плана за раз.** Не строить всю систему сразу.
  Если задача расплывчата — остановись и спроси, а не выдумывай требования.
- **Не нарушай принципы раздела 3.** Особенно: не превращай детерминированную работу
  в LLM-вызовы; не давай Executor свободный ReAct; инварианты безопасности — в коде.
- **Каждый узел: строгий Pydantic-вход и выход.** LLM-узлы — через `with_structured_output`.
- **Пиши тесты** для детерминированных узлов (Spec Parser, Validator, flattening, метрики).
- **Отладка на qwen2.5:14b** локально. Помни про слабость 14B в structured output
  и рассуждении — чем у́же задача узла, тем лучше.
- **Объясняй решения автору** (он учится) и честно поправляй неудачные идеи.
- **Не делай необратимых операций** без подтверждения. Подключённая папка — только проект.

## 13. Эталонный сценарий для проверки системы (аренда авто)

```
Поиск авто (город, даты, класс)  → возвращает carId, searchSessionId
   ↓ (carId)
Предв. бронирование              → возвращает bookingDraftId, price
   ↓ (bookingDraftId)
Подтверждение + блокировка авто   → возвращает confirmedBookingId
```
Использовать как первый реальный тест Scenario Analyst (этап 3) и сквозного исполнения.
Ключевые проверки: правильная передача данных между шагами; негативы на уровне потока
(нарушенный порядок, протухший bookingDraftId, двойное подтверждение); teardown (отмена).
